# Claude Code Project Guidelines

## Frontend / Angular Stack Conventions
This project follows the team's **Angular 22+** conventions documented in [`skills/desarrollo-buenas-practicas/SKILL.md`](./skills/desarrollo-buenas-practicas/SKILL.md) (or `~/.claude/skills/desarrollo-buenas-practicas/SKILL.md`):

- **Reactivity**: Strictly **Signals**. Never use `effect()` except the narrow cases in §2.7 (use `computed()` or `linkedSignal()`).
- **Data Fetching**: Resource API only (`httpResource`, `rxResource`, `resource`).
- **Forms**: Signal Forms (`@angular/forms/signals`). Never Reactive Forms or `ngModel`.
- **Change Detection**: Zoneless (`provideZonelessChangeDetection()`). Check `@angular/core` in `package.json`: v22+ do not specify `changeDetection` (OnPush is default); below v22 always set `ChangeDetectionStrategy.OnPush`. `standalone: true` only in v18 or lower.
- **Templates**: Native control flow (`@if`, `@for`, `@switch`, `@let`), `@defer`, and `NgOptimizedImage`.
- **Styling**: SCSS with BEM methodology, elements and modifiers always nested with `&__` / `&--` (never the full class rewritten, never `&__title--big`). Avoid `::ng-deep`. `@use` without relative paths (`@use 'notificaciones/notificaciones-header' as notif;`, via `includePaths: ["src/assets/styles"]`); module partials live in `assets/styles/<module>/_<module>-<part>.scss`. When SCSS repeats, extract it to its ITCSS (inverted triangle) layer: token, `@mixin`, `.o-*` object or `.u-*` utility. Never copy it or use `@extend`.
- **Same-route navigation**: To reset state on a link to the current route, recreate the component with `router.routeReuseStrategy.shouldReuseRoute = () => false` (plus `onSameUrlNavigation: 'reload'`) and restore it in `DestroyRef.onDestroy`. Do not reset state by hand.
- **Architecture**: Vertical slices / feature-based folder structure. No filename/class suffixes for components, services and directives (`user-list.ts` exports `UserList`); pipes, guards, resolvers and interceptors keep it (`currency-format-pipe.ts` exports `CurrencyFormatPipe`, `auth-guard.ts` exports `authGuard`). Backend contract types match the C# names: `<Action><Entity>Request` for what is sent, `<Entity>Response` for what comes back; map to a front model only when the view needs another shape (§2.11).
- **Size**: Max 200 lines per component `.ts` or template `.html`, 250 per service, 150 per `.scss`. Split by responsibility.
- **Subcomponents**: Never a `components/` folder inside a feature. Nest each child inside its parent's folder. Only `shared/components/` is allowed, for components reused across features.
- **No over-engineering**: Do not split into subcomponents unless the file exceeds its size limit, the block is reused, or it has its own logic; small one-off blocks stay in the parent template. Simplest solution that solves today's request. No abstractions, layers, generics, tokens or libraries "just in case"; abstract only when code appears a second time (§11.7.1).
- **No test files, but always test that it works**: Never create test files (`*.spec.ts`, `*.test.ts`, `tests/`) unless the user explicitly asks for them. Set `skipTests: true` in `angular.json` schematics. Verify with build, lint and (except trivial changes) manual testing in the app, done by the agent in a browser it controls with screenshots as evidence when it has one, otherwise handed to the user as concrete steps (`references/08-sin-tests.md` §8.3).
- **Reuse**: Before creating a component, search for an existing one. Repeated UI (user picker, data table, search box) becomes one reusable component, never adapted copies (`references/01-project-structure.md` §1.5).
- **AI files in `.gitignore`**: Make sure the project `.gitignore` excludes every AI/agent file (`.claude/`, `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `graphify-out/`, `tasks/todo.md`...). Ask before `git rm --cached` (§10.9).
- **Security (always)**: Every change passes the quick Red Team table in `references/15-security.md` §15.2; high risk adds the deep offensive review (§11.3). **Dependency audit always**: run `npm audit` and `npm audit --omit=dev` when starting in a project, and after any change to `package.json`/lockfile (CI repeats it and blocks the merge); report every finding, flag runtime `high`/`critical`, never `npm audit fix --force` without asking (§15.10). Never disable protections (sanitizer, CSP, XSRF, backend validation), never use `bypassSecurityTrust*` with external data, never store tokens in `localStorage`, never put secrets in the front. Report every vulnerability found, even out of scope. **When asked for security** ("audit this", "is it safe?"): run §15.14, which reviews every security area (each one OK / finding / N/A) and goes deeper with that area's skill (`offensive-*`, Anthropic-Cybersecurity-Skills, Cloudflare `security-audit`, `claude-security`) where there is a finding, the area is sensitive or the scope is large.
- **Reference Manuals**: For details on each area, inspect `references/*.md` inside the skill directory.

## Agent Efficiency (always on)
See `references/14-agent-efficiency.md`.

- **Adapt to the agent and models in use**: Model and tool names in the skill (Opus, Sonnet, Haiku, `/compact`, `AskUserQuestion`) are examples. Detect which agent and models are available and use the equivalent. Rules never change, only syntax (§14.7).
- **Caveman mode**: Terse replies, no filler. One short status line when starting a new phase or before a long-running step. Technical terms, code and errors exact. Normal prose only for security warnings, irreversible actions, code, commits, PRs and docs.
- **Library lookups**: Before researching a library, check for another open agent session (`ListAgents`) that knows it and ask it (`SendMessage`). Then docs MCP, then `node_modules`, then web.
- **Orchestrate, delegate only when it saves tokens**: The selected model plans, decides and always reviews. Delegate to the team subagents (`investigador`, `ejecutor`, `revisor-checklist`; if missing, an installed compressed equivalent such as `cavecrew-*`, else `Agent` with a cheaper `model`) large searches/reads (3+ files, logs, docs) and mechanical edits across 8+ files, in parallel when independent; do small tasks yourself (§14.3.4). For a codebase-wide change that splits into 5+ independent units, propose `/batch <instruction>` (one background subagent per unit, each in its own worktree). Shared context in `tasks/brief-<task>.md`. Executors never guess: when stuck they return `NECESITA_ADVISOR: <question>`. Native advisor (`/advisor`): off by default (measured: Sonnet + Opus advisor cost 10x and widened scope); if the user turns it on, call it after orienting, when stuck and before declaring done; never for mechanical steps. Briefs carry only the compact skill rules that apply (§14.3.5). Before compacting, add the 5-line session summary (goal, findings, done, next, files) to the `tasks/todo.md` Log (§14.4).
- **Ask upfront**: Before non-trivial work, ask all questions that change the result in one turn, with options and a recommended one (`AskUserQuestion`). Do not ask what the repo already answers.
- **Working loop**: state the assumptions you made without asking in one line. Before coding each task, define a done-check you can run or see, and finish only when it passes. When two sources disagree (request vs skill, two instruction files, code vs docs), show both and ask; never pick one silently. Let commands answer what commands can (`graphify query`, grep, compiler). Report every check you skipped: "build OK" is false if lint or the manual test was skipped. Judge build and lint by new errors only. After 3 failed fixes of the same error, stop and report the blocker with the exact error. When resuming, check the `tasks/todo.md` Estado against `git log` and the build first (§11.2, §11.3, §11.6). In the final report, list the decisions you made that the request did not fix, and say what each passing check covered and what it did not. Record every user correction in `tasks/lessons.md` and read it at session start (§11.8).
- **Classify and review by risk**: Read-only requests stay read-only. Classify: small if it can be resumed from the request plus `git diff` (work inline); large otherwise (`tasks/todo.md` with L1 = verbatim request, Specs, Tasks with risk, Log; one task at a time; commits of ~400 lines). Review by risk: trivial (no behavior change: copy, plain styles, static HTML, mechanical rename) = diff + build/lint + quick §15.2 table, medium = + `ponytail-review`, high (auth, tokens, interceptors, permissions, sensitive data, `package.json`, deleting or migrating data) = + independent reviewer + deep offensive review with the area's skill (§11.2, §11.3, §15.14). Delegate only for a named reason: big exploration, parallel writers, context backstop, verifier of a high-risk task or of a large diff (3+ files) against the checklist; when in doubt, work inline (§14.3.4).
- **Auto-compact**: At the end of each phase or before an unrelated task, save state to `tasks/todo.md` and suggest the user run `/compact` with focus (keep decisions, touched files, pending items); you cannot run it yourself. Never mid-change or with a pending question.
- **Graphify startup (mandatory, first action of every session, before searching, reading or editing)**: run `graphify --help`, `graphify hook status` and `graphify update .`. Command not found → `pip install graphifyy && graphify install`. `warning: skill is from graphify X, package is Y` → `pip install --upgrade graphifyy && graphify install`. Hooks not installed → `graphify hook install` + `graphify claude install`. Then the first search on the code is always `graphify query "<question>"`; it shows where to look for far fewer tokens than grep or reading files. Skip it only when the user named the exact file and line. After editing files (before the final answer) or before compacting: `graphify update .`.
- **Agent tools (always)**: ponytail (minimal code, `ponytail-review` on the diff for every non-trivial change (§11.3)); agent-skills by phase, never the test-writing ones; `claude-automation-recommender` (claude-code-setup) once in repos without setup. Headroom starts on its own through SessionStart hooks. Security scan for a feature- or repo-wide audit: the `claude-security` plugin (§15.14); high-risk changes (§11.3): the matching `offensive-*` skill (claude-red), only against the project's own code (§15.2). If one is missing, install it and say so in one line (§14.8).
